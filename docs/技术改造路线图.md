# WHYFXPG 技术改造路线图

> 改造目标：从"海关内部评分工具"转变为"进出口合规风险情报 API 平台"
> 文档版本：V1.0
> 日期：2026-08-06

---

## 一、技术改造的核心命题

当前系统是**单机工具**，面向少数内部用户（海关检验人员）。改造后是**多租户 SaaS 平台**，面向万级的外部企业客户。

这意味着技术改造要回答三个问题：

1. **如何让外部企业客户安全地接入系统？** → 认证、授权、多租户隔离
2. **如何让系统从"工具"变成"可计量的服务"？** → API Gateway、计量计费、用量监控
3. **如何让平台从"单一功能"变成"风险情报网络"？** → 数据源扩充、数据服务化、网络效应

### 3.3 数据源接入标准化（SourceAdapter 接口）

当前每个数据源写一个适配器，没有统一接口。新增标准接口：

```python
from whyfxpg.adapters.sources import BaseSourceAdapter, SourceResponse

class BaseSourceAdapter(ABC):
    """所有数据源适配器的基类"""

    @property
    def source_id(self) -> str:
        raise NotImplementedError

    @property
    def source_name(self) -> str:
        raise NotImplementedError

    @abstractmethod
    def fetch(self, since: datetime = None) -> List[SourceResponse]:
        """从数据源获取原始页面，返回标准化响应"""
        ...

    @abstractmethod
    def parse(self, raw: SourceResponse) -> RiskEvent:
        """将原始响应解析为 RiskEvent"""
        ...

    def health_check(self) -> bool:
        """健康检查，返回数据源是否可达"""
        ...
```

**接入新数据源的完整流程**（以 RAPEX 为例）：

```python
# 继承基类，3 个方法搞定一个新数据源
class RapexAdapter(BaseSourceAdapter):
    source_id = "RAPEX"
    source_name = "欧盟 Safety Gate"

    def fetch(self, since=None):
        # 调用 RAPEX 开放数据 API
        ...

    def parse(self, raw: SourceResponse) -> RiskEvent:
        # 字段映射逻辑
        ...

# 注册到全局数据源注册表
SourceRegistry.register(RapexAdapter())

# 统一调度
for adapter in SourceRegistry.all():
    events = adapter.fetch()
    for raw in events:
        event = adapter.parse(raw)
        RiskEventStore.add(event)
```

## 四、Phase 1：API 平台（Week 9–24）

**目标**：构建完整的 REST API 平台，支持多租户、API Key 认证、按量计费。

### 4.1 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| API 框架 | FastAPI | 高性能、自动 OpenAPI 文档、与现有 Python 代码无缝集成 |
| 数据库 | PostgreSQL | 多租户支持、JSON 字段、事务、水平扩展 |
| 缓存 | Redis | API 计量计数、会话管理、评分结果缓存 |
| 原始文件存储 | S3 兼容存储（MinIO） | 原始页面/报告二进制存储 |
| API Gateway | FastAPI + 中间件（自建） | 不引入 Kong 等重型组件，用 FastAPI 中间件实现认证/限流 |
| 部署 | Docker + Docker Compose | 一键部署，客户私有化安装也方便 |
| 文档 | OpenAPI 3.0（Swagger） | 自动生成 API 文档和客户端 SDK |

### 4.2 数据库改造：SQLite → PostgreSQL

**迁移策略**：两阶段迁移

```
Phase 1a（Week 9-12）：
  - PostgreSQL 作为主库，SQLite 保留为只读归档
  - 逐步把写入操作迁移到 PostgreSQL
  - 验证评分结果一致性

Phase 1b（Week 13-16）：
  - 废弃 SQLite，全量切换到 PostgreSQL
  - 重写所有 stores/ 为 Repository 模式，对接 PostgreSQL
  - 建立数据迁移自动化脚本（ Alembic）
```

### 4.3 API Gateway 功能

用 FastAPI 中间件实现，不需要单独部署 Kong：

```python
# 认证中间件
@app.middleware("http")
async def api_key_auth(request: Request, call_next):
    api_key = request.headers.get("X-API-Key")
    if not api_key:
        return JSONResponse(status_code=401, content={"error": "API Key required"})

    # 验证 API Key，查询账户信息
    account = await AccountService.verify_key(api_key)
    if not account:
        return JSONResponse(status_code=403, content={"error": "Invalid API Key"})

    # 检查额度
    if account.plan_type != "enterprise":
        usage = await MeteringService.get_monthly_usage(account.id)
        if usage >= account.monthly_quota:
            return JSONResponse(status_code=429,
                content={"error": "Monthly quota exceeded",
                         "quota": account.monthly_quota,
                         "reset_at": account.quota_reset_at})

    # 注入 account 到请求上下文
    request.state.account = account
    return await call_next(request)
```

**限流策略**：

| 计划类型 | QPS 限制 | 每日上限 | 每月上限 |
|---------|---------|---------|---------|
| Trial | 1 req/s | 100 | 1,000 |
| Basic | 5 req/s | 5,000 | 50,000 |
| Pro | 20 req/s | 50,000 | 500,000 |
| Enterprise | 自定义 | 自定义 | 自定义 |

### 5.2 多语言处理架构

当前系统无多语言能力，这是 Phase 2 最大的技术挑战：

```
原始页面（任意语言）
    │
    ▼
┌─────────────────┐
│  语言检测模型    │  ← fastText 轻量语言检测（支持 150+ 语种）
│  (langdetect)   │
└────────┬────────┘
         │ 输出：lang_code (ISO 639-1)
         ▼
┌─────────────────────────────────────────┐
│           路由决策                       │
├──────────────────┬──────────────────────┤
│  英语/日语/韩语  │  其他语言             │
│  直接解析        │  多语言 LLM 抽取      │
└──────────────────┴──────────────────────┘
         │
         ▼
┌─────────────────────────────────────────┐
│  多语言 LLM 抽取服务（可选）              │
│  - 调用 MiniMax / Kimi / Azure OpenAI   │
│  - Prompt 模板化，输入原文，输出结构化 JSON│
│  - 降级策略：检测到不支持语种 → 标记待人工 │
└─────────────────────────────────────────┘
```

**多语言 LLM 抽取 Prompt 模板**：


### 5.3 数据网络效应的建立

**为什么要 20+ 数据源**：数据源越多，跨数据源消重和关联的价值越高。

```
单一数据源的问题：
  - CPSC 收录的某事件，RAPEX 可能也有
  - 单一来源可能漏采（网站维护、访问限制）
  - 无法发现"同一制造商在不同地区的风险信号叠加"

跨数据源关联的价值：
  - 跨源消重：同一制造商同一产品的多源报道 → 确认为高置信度风险事件
  - 跨源增强：单一来源评分 60，跨三源确认为 85 → 风险等级升级
  - 跨源发现：某制造商仅在 RAPEX 出现，但通过商业关联扩展到中国进口商
```

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| LLM 多语言抽取成本失控 | 中 | 高 | 严格按语言路由，非英语仅在置信度 < 0.7 时调用 LLM；缓存已抽取结果 |
| 数据源网站结构变更导致解析失败 | 高 | 中 | 每个数据源实现健康检查，连续 3 次失败自动降级并告警 |
| PostgreSQL 水平扩展复杂度 | 低 | 高 | Phase 2 再考虑，Phase 1 先用主从复制撑住 |
| API Key 被盗用/泄露 | 中 | 极高 | 实施 Key 轮换机制，支持账户侧撤销 Key |
| 多租户数据隔离失效 | 低 | 极高 | 每次查询强制带上 account_id，PostgreSQL 行级安全策略兜底 |

## 九、总结：改造路径

| 阶段 | 时间 | 核心工作 | 交付物 |
|------|------|---------|--------|
| **Phase 0** | Week 1-8 | 核心资产封装 + Python 包发布 | whyfxpg pip 包 + 2-3 家报关行试用 |
| **Phase 1** | Week 9-24 | API 平台 + 多租户 + 计费 | FastAPI REST API + 企业账户系统 |
| **Phase 2** | Week 25-52 | 数据源扩充 + 多语言处理 | 20+ 数据源 + 多语言 NLP 能力 |

**技术改造的核心原则**：

1. **保留核心，替换外壳**：评分引擎、规则引擎、采集管道是核心资产，不重写；UI、数据库、部署方式是外壳，逐步替换
2. **先验证，后投入**：Phase 0 用最小成本验证市场是否存在，Phase 1 再投入构建平台
3. **数据源是护城河**：20+ 数据源的接入和维护是平台最持久的竞争力，任何竞品复制都需要数年时间

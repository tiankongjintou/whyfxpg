# WHYFXPG 自主运行方案

> 让 WHYFXPG 项目在无人值守情况下长期自主推进的质量保障体系

---

## 一、核心设计思想

Hermes 的设计不是"你问我答"，而是**事件驱动的自主智能体网络**。实现"长程自主决策、保质保量完成"需要四个系统同时运行：

```
用户（偶尔介入）
    │  ← 仅处理：重大决策 / 预警通知 / 方向调整
    ▼
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│  通讯层：Gateway（消息通道）                │
│  - 接收用户指令（飞书/微信/Telegram）       │
│  - 推送进度/预警/决策请求到用户             │
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    ▼
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│  记忆层：Skills + Memory（知识沉淀）         │
│  - 项目开发规范（SKILL）                    │

│  - 跨 session 的上下文延续                  │
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    │
    ▼
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 二、具体实施步骤

### Step 1：建立项目开发规范 Skill

创建 `whyfxpg-dev` Skill，作为所有自主开发行为的标准操作程序：

```
whyfxpg-dev skill 内容：
  - 开发阶段定义（Phase 0 / Phase 1 / Phase 2）
  - 每个阶段的任务分解和验收标准
  - 代码质量门禁（测试覆盖率、lint、类型检查）
  - Commit 规范和分支策略
  - PR/MR 审查清单
  - 文档更新要求（每次功能变更必须同步更新文档）
```

### Step 2：创建 Kanban 工作板

用 Hermes Kanban 建立项目任务跟踪：

```
列：待办 | 进行中 | 阻塞 | 已完成 | 验收通过
```

**每个 Phase 的任务全部卡片化**：

```
Phase 0 任务卡示例：
  - [ ] P0-1: 修复风险等级阈值 Bug（S≥8000 → S≥85）
  - [ ] P0-2: risk_events 表增加 extracted_language 字段
  - [ ] P0-3: 创建 whyfxpg Python 包，发布到 PyPI
  - [ ] P0-4: 封装 RiskScorer 为独立 assess() 接口
  - [ ] P0-5: 编写 whyfxpg 包 API 文档
  - [ ] P0-6: 接触 2-3 家报关行进行封闭试用

Phase 1 任务卡示例：
  - [ ] P1-1: 搭建 FastAPI 项目骨架
  - [ ] P1-2: 实现 API Key 认证中间件
  - [ ] P1-3: PostgreSQL 迁移脚本编写
  - [ ] P1-4: 实现 /api/v1/events 端点
  - [ ] P1-5: 实现账户注册和 API Key 发放
  - ...（按优先级排列）
```

### Step 3：建立三层 Cron 巡检机制

```
【每小时 Cron：轻量检查】
触发条件：每小时的第 5 分钟
任务：
  1. 检查数据采集管道是否正常（数据源是否可访问）
  2. 检查数据库是否有新增风险事件
  3. 检查是否有预警触发
  4. 若发现异常：发消息给用户 + 记录到 Memory

【每天 Cron：开发进度检查】
触发条件：每天早上 9:00
任务：
  1. 从 Kanban 领取一个"待办"任务
  2. 执行该任务（开发/测试/文档）
  3. 更新 Kanban 卡片状态
  4. 若任务完成且通过质量门禁，自动领取下一个
  5. 若遇到阻塞，记录阻塞原因，发消息给用户请求决策

【每周 Cron：完整质量回顾】
触发条件：每周一 10:00
任务：
  1. 运行完整测试套件，生成测试报告
  2. 检查代码覆盖率是否达标（> 70%）
  3. 运行 lint 和类型检查
  4. 更新文档，确认文档与代码同步
  5. 生成周报发给用户
  6. 识别下周优先级最高的 3 个任务卡
```

### Step 4：配置质量门禁

在项目根目录建立 `.hermes/HERMES_RULES.md`：

```markdown
# WHYFXPG 开发质量门禁

## 必须满足才能 Commit/PR 的条件

1. **测试通过**：`pytest tests/ -v`，不允许有 FAILED 测试
2. **Lint 通过**：`ruff check whyfxpg/`，不允许有 ERROR
3. **类型检查**：`mypy whyfxpg/`，不允许有 ERROR
4. **覆盖率达标**：新增代码覆盖率 ≥ 70%
5. **文档同步**：如果改了 API 或数据模型，必须同步更新 docs/ 下的对应文档

## 自动检查流程

每次 `git commit` 或打开 PR 时自动运行上述检查。
检查失败 → Commit/PR 被拒绝，错误信息发给用户。
```

### Step 5：配置消息通知（Gateway）

将 Hermes 连接到飞书/微信/Telegram，让用户在不在电脑前时也能：

```
收到通知的类型：
  ✅ 任务完成通知（重要任务完成后告知用户）
  ⚠️ 阻塞通知（遇到无法自行解决的决策，升级给用户）
  🔴 异常告警（数据采集失败、系统错误、数据质量问题）
  📊 周报（每周一早上推送上周进度 + 本周计划）
  ❓ 决策请求（需要用户拍板的重大选择）
```

## 三、实际执行流程示例

### 场景：连续 7 天无人值守运行

**Day 1（用户设定目标）**：
```
用户（飞书）："继续 Phase 0 的开发，先把 P0-1 修好"
Hermes：
  1. 创建 P0-1 任务卡到 Kanban
  2. 分析代码，找到 risk_scorer.py 中的阈值硬编码
  3. 修复：thresholds["S"] = 85（而非 8000）
  4. 写测试用例覆盖 S=85 边界值
  5. 运行测试，验证通过
  6. 更新文档（05-核心算法说明书.md）
  7. 推送完成通知给用户
  8. 领取 P0-2 任务卡
```

**Day 2–3（自动推进）**：
```
每天 Cron 自动执行：
  1. 领取 P0-2 任务（extracted_language 字段）
  2. 编写 Alembic 迁移脚本
  3. 修改 extract_engine.py 调用语言检测
  4. 写测试，验证字段被正确填充
  5. 更新数据库设计说明书（03-数据库设计说明书.md）
  6. 继续 P0-3（Python 包发布）
```

**Day 4（遇到阻塞）**：
```
每天 Cron 领取 P0-4 任务时发现：
  - RiskScorer 依赖 risk_model.yaml 的加载逻辑
  - 现有实现与 YAML 强耦合，无法独立发布为包

升级通知发给用户：
  "P0-4 遇到阻塞：RiskScorer 依赖 YAML 配置文件。
   两个方案：
   A. 将 YAML 改为 Python 对象内嵌（简单，但修改不灵活）
   B. 将 YAML 路径改为可注入依赖（更干净，但需要重构接口）
   请选择：A 或 B"

用户（飞书）："B"
Hermes：按方案 B 执行，继续开发
```

**Day 5–7（继续推进）**：
```
Day 5: 完成 RiskScorer 重构，发布 Python 包到 PyPI
Day 6: 完成 API 文档编写，补充使用示例
Day 7: 领取 P0-6，联系报关行试用

每周 Cron 生成周报发给用户：
  "本周完成：P0-1 ✅ P0-2 ✅ P0-3 ✅ P0-4 ✅
   下周计划：P0-5（API文档）→ P0-6（报关行试用）
   阻塞解决：YAML 依赖重构选择方案 B，已完成"
```

## 四、自主演进的保障机制

### 4.1 决策规则（避免事事请示）

提前在 Skill 中定义决策规则，减少升级：

```
【自主决策范围】（不需请示用户）
  - 代码风格和实现细节
  - 测试用例设计
  - 变量命名和函数拆分
  - 文档措辞和格式
  - 依赖包版本升级（小版本）
  - Bug 修复的具体实现方式

【必须升级的决策】（发消息给用户）
  - 需求变更（发现需求书定义与代码不一致）
  - 技术选型重大变更（如更换数据库、更换 API 框架）
  - 发现需要 2 天以上工作量才能完成的任务
  - 测试覆盖率低于 50% 且无法快速达标
  - 发现 P0 安全漏洞
```

### 4.2 质量保障机制

```
【每次 Commit 自动检查】
  → Ruff lint（代码风格）
  → Mypy 类型检查
  → Pytest 测试（失败即拒绝 commit）

【每天开发前检查】
  → 拉取最新代码，确认无冲突
  → 运行完整测试套件
  → 确认文档与代码同步

【每周质量门禁】
  → 代码覆盖率报告（< 70% 则预警）
  → 安全扫描（bandit）
  → 依赖包安全检查（pip-audit）
```

### 4.3 进度透明机制

```
【Kanban 是进度真相的唯一来源】
  - 所有任务都在 Kanban 上
  - 每天 Cron 更新卡片状态
  - 用户任何时候都能看到真实进度

【周报模板】
  ## WHYFXPG 周报（Week N）

  ### 本周完成
  - [卡片名] @hermes 2026-08-10 ✅

  ### 下周计划
  - [优先级最高 3 张卡片]

  ### 阻塞与决策
  - [如有：描述 + 用户选择的方案]

  ### 质量指标
  - 测试覆盖率：78%（较上周 +3%）
  - 代码行数：12,450 行
  - 数据源在线率：100%
```

## 六、快速启动命令

以下命令在 Hermes CLI 中一次性执行，即可启动自主运行系统：

```bash
# 1. 创建项目开发 Skill
hermes skills install <whyfxpg-dev-skill-url>

# 2. 初始化 Kanban 板
hermes kanban init whyfxpg
hermes kanban create "P0-1: 修复风险等级阈值 Bug" --board whyfxpg
hermes kanban create "P0-2: extracted_language 字段" --board whyfxpg
hermes kanban create "P0-3: Python 包发布" --board whyfxpg
...（按任务清单创建所有 Phase 0-2 卡片）

# 3. 创建每日 Cron（开发进度推进）
hermes cron create "every day 9:00" \
  --name "WHYFXPG 日开发" \
  --skill "whyfxpg-dev" \
  --deliver "telegram" \
  --prompt "从 Kanban whyfxpg 领取一个最高优先级任务，执行开发和测试，更新卡片状态。若遇到阻塞，记录原因并请求用户决策。"

# 4. 创建每小时 Cron（健康检查）
hermes cron create "every 1h" \
  --name "WHYFXPG 健康检查" \
  --deliver "telegram" \
  --prompt "检查数据采集管道状态和新增风险事件，若发现异常（连续3次失败、数据量异常、质量问题）发预警通知。"

# 5. 创建每周 Cron（质量回顾）
hermes cron create "0 10 * * 1" \
  --name "WHYFXPG 周质量报告" \
  --deliver "telegram" \
  --prompt "运行完整测试套件和覆盖率报告，更新 Kanban 进度，生成周报发给用户。"

# 6. 配置飞书/Telegram Gateway 通知
hermes gateway setup
```

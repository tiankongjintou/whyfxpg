# WHYFXPG 模块接口契约文档

## 1. 设计原则

- **模块独立**：每个模块是独立Python文件，不直接调用其他业务模块。
- **数据库为总线**：模块之间通过读写约定的数据库表交换数据。
- **配置驱动**：所有模块读取 `config/` 目录下的YAML配置。
- **可替换**：任何模块都可以被其他AI工具开发的等价模块替换，只要遵守本契约。
- **统一返回格式**：每个模块主入口 `run()` 返回统一字典。

---

## 2. 统一返回格式

每个模块的 `run()` 方法必须返回：

```python
{
    "module": "模块ID",          # 如 "fetcher", "risk_model"
    "status": "success",         # success / partial / error
    "records_processed": 0,      # 处理记录数
    "records_created": 0,        # 新创建记录数
    "errors": [],                # 错误信息列表
    "message": "描述信息"
}
```

## 3. 模块清单与接口

### M0: 数据库初始化 (whyfxpg.core.db)

- **输入**：无
- **输出**：创建SQLite数据库及所有表
- **调用方式**：
  ```python
  from whyfxpg.core.db import init_db, get_db_connection
  init_db()
  conn = get_db_connection()
  ```

### M1: 配置版本管理 (whyfxpg.core.config_version)

- **输入**：`config/` 下所有YAML文件
- **输出**：`config_versions` 表
- **入口**：`ConfigVersionManager(config_dir, db_path).run()`
- **主要方法**：
  - `compute_hashes()`: 计算配置哈希
  - `create_version()`: 检测变化并记录新版本
  - `get_latest_db_version()`: 获取最新版本
- **数据库契约**：
  - 写入 `config_versions` 表
  - 每条记录包含 `version_id`, `file_hashes`, `config_snapshot`

### M2: 数据采集 (whyfxpg.core.fetcher)

- **输入**：
  - `config/sources.yaml`
  - `monitor_sources` 表（状态）
- **输出**：
  - `raw_pages` 表：原始页面内容
  - `crawl_logs` 表：采集日志
  - `monitor_sources` 表：更新状态
- **入口**：`Fetcher(config_dir, db_path).run()`
- **处理逻辑**：
  1. 读取 `config/sources.yaml` 初始化 `monitor_sources`。
  2. 对每个启用来源执行HTTP请求。
  3. 计算内容哈希，与数据库中已有哈希对比。
  4. 只有新内容才写入 `raw_pages`。
  5. 更新 `monitor_sources` 状态。
- **状态字段**：
  - `raw_pages.status`: `fetched` / `parsed` / `failed`
- **可替换说明**：
  - 可替换为更复杂的分布式爬虫、Playwright动态抓取、RSS解析器等。
  - 替换后仍需写入 `raw_pages` 表，并正确设置 `status='fetched'`。

### M3: 信息抽取 (whyfxpg.core.extract_engine)

- **输入**：
  - `raw_pages` 表中 `status='fetched'` 的记录
  - `config/extract_rules.yaml`
  - `config/keywords.yaml`
- **输出**：`risk_events` 表（未评分状态）
- **入口**：`ExtractEngine(config_dir, db_path).run()`
- **处理逻辑**：
  1. 读取 `raw_pages` 中未解析的页面。
  2. 根据抽取规则提取字段。
  3. 写入 `risk_events`。
  4. 将 `raw_pages.status` 更新为 `parsed`。
- **关键字段**：
  - `risk_events.ss_score`: 初始为NULL
  - `risk_events.ps_score`: 初始为NULL
  - `risk_events.review_status`: `auto`
- **可替换说明**：
  - 可替换为基于LLM的抽取模块。
  - 替换后仍需写入 `risk_events` 表，且 `ss_score` 和 `ps_score` 为NULL，由评分模块处理。

### M4: 风险评分 (whyfxpg.core.risk_model)

- **输入**：
  - `risk_events` 表中 `ss_score IS NULL` 或 `ps_score IS NULL` 的记录
  - `config/risk_model.yaml`
- **输出**：
  - 更新 `risk_events` 表（补全评分和等级）
  - `product_risk_summary` 表
  - `country_risk_summary` 表
  - `enterprise_risk_summary` 表
- **入口**：`RiskModel(config_dir, db_path).run()`
- **计算流程**：
  1. 读取未评分事件。
  2. 根据严重度等级计算 `ss_score`。
  3. 根据历史事件密度计算 `ps_score` 和概率等级。
  4. 计算国别、产品、历史、证据修正系数。
  5. 计算综合得分 `total_score` 和风险等级 `rs_level`。
  6. 更新 `risk_events` 表。
  7. 重新生成汇总表。
- **关键字段**：
  - `risk_events.total_score`
  - `risk_events.rs_level` (S/M/L/A)
  - `risk_events.config_version`
  - `risk_events.model_version`
- **可替换说明**：
  - 可替换为更复杂的贝叶斯模型、机器学习模型、专家系统等。
  - 替换后仍需写入 `risk_events` 的评分字段和三个汇总表。

### M5: 预警生成 (whyfxpg.core.alert_engine)

- **输入**：
  - `risk_events` 已评分记录
  - `product_risk_summary` / `country_risk_summary` / `enterprise_risk_summary`
  - `config/alert_rules.yaml`
- **输出**：`alert_records` 表
- **入口**：`AlertEngine(config_dir, db_path).run()`
- **处理逻辑**：
  1. 读取预警规则。
  2. 根据规则条件查询数据库。
  3. 触发预警并写入 `alert_records`。
  4. 避免重复触发（状态为 `pending` 或 `confirmed` 的相同预警不再插入）。
- **关键字段**：
  - `alert_records.status`: `pending` / `confirmed` / `resolved` / `ignored`
- **可替换说明**：
  - 可替换为更复杂的时序分析、异常检测、规则引擎等。
  - 替换后仍需写入 `alert_records` 表。

### M6: 报告生成 (whyfxpg.core.report_generator)

- **输入**：所有数据库表
- **输出**：Word文件、Excel文件
- **入口**：`ReportGenerator(db_path, output_dir).run()`
- **输出文件**：
  - `reports/word/进口机电产品风险评估报告_YYYYMMDDhhmmss.docx`
  - `reports/excel/进口机电产品风险明细_YYYYMMDDhhmmss.xlsx`
- **可替换说明**：
  - 可替换为PDF生成、PPT生成、邮件发送等模块。
  - 替换后只需输出文件即可，不写入数据库。

### M7: 数字化看板 (whyfxpg.webui.app)

- **输入**：所有数据库表
- **输出**：Streamlit Web界面
- **入口**：`streamlit run whyfxpg/webui/app.py`
- **可替换说明**：
  - 可替换为Flask/FastAPI/Dash等Web框架。
  - 只需读取数据库表展示，不修改核心数据。

### M8: 人工复核 (whyfxpg.webui.app 复核面板 + whyfxpg.core.feedback_learner)

- **状态**：已实现。
- **输入**：`risk_events` 和 `alert_records`
- **输出**：`manual_reviews` 表；经复核后 `risk_events.review_status` 更新为 `approved`/`rejected`；反馈学习会调整国别/产品/制造商系数。
- **入口**：
  - Web UI：在“人工复核”页面勾选事件，选择 `approved`/`rejected` 并提交。
  - 批量学习：`python -m whyfxpg.core.feedback_learner`。
- **处理逻辑**：
  1. 看板读取 `review_status='pending'` 或 `='auto'` 的事件。
  2. 用户提交复核结果，写入 `manual_reviews`。
  3. `feedback_learner` 读取复核记录，计算偏差并修正系数。
- **可替换说明**：
  - 可替换为命令行复核工具或外部审批系统。
  - 替换后仍需写入 `manual_reviews` 表并调用 `feedback_learner` 完成反馈闭环。

## 6. 模块替换指南

如果你用其他AI工具（如OpenCode、Claude Code）开发了某个模块的替代版本，请按以下步骤集成：

1. **保持类名和入口方法一致**：
   - 类名：如 `Fetcher`, `ExtractEngine`, `RiskModel`, `AlertEngine`, `ReportGenerator`
   - 入口方法：`run()`

2. **保持构造函数一致**：
   - 至少接受 `config_dir` 和 `db_path` 两个参数。

3. **保持数据库契约**：
   - 输入表必须读取本模块约定输入表的数据。
   - 输出表必须写入本模块约定输出表的字段。

4. **保持返回格式一致**：
   - 返回统一字典，包含 `module`, `status`, `records_processed`, `records_created`, `errors`, `message`。

5. **保持配置文件契约**：
   - 如果模块读取配置，必须兼容现有YAML结构。
   - 如需新增字段，应追加字段并在文档中说明。

6. **测试集成**：
   - 单独运行该模块。
   - 检查数据库输出是否正确。
   - 运行全链路入口验证兼容性。

## 7. 全链路运行入口

```bash
python whyfxpg/main.py
```

或者分步运行：

```bash

python -m whyfxpg.core.fetcher
python -m whyfxpg.core.extract_engine
```

## 8. 注意事项

- 数据库路径默认为 `whyfxpg/data/whyfxpg.db`，可通过环境变量 `WHYFXPG_DB_PATH` 修改。
- 配置目录默认为 `config/`，可通过环境变量 `WHYFXPG_CONFIG_DIR` 修改。
- 所有模块优先从环境变量读取路径，否则使用默认值。
- LLM相关功能需要 `.env` 文件中配置API密钥。

## 9. 测试与运行保障

### 9.1 单元测试

- 已新增 `whyfxpg/tests/` 目录，使用 `pytest` 运行。
- 覆盖模块：
  - `test_db.py`：表结构、WAL 模式、并发写入不锁死。
  - `test_config_version.py`：配置版本检测与自动递增。
  - `test_fetcher.py`：HTTP 请求 mock、哈希去重、日志写入。
  - `test_extract_engine.py`：正则抽取、关键词映射、日期归一化、事件入库。
  - `test_risk_model.py`：评分计算、风险等级映射、汇总表更新。
  - `test_alert_engine.py`：高严重度、国别聚集等规则触发。
- 所有测试使用临时数据库（`tmp_path`）和临时配置目录，不污染生产数据。
- 测试中自动禁用真实 LLM 调用，保证离线可跑。
- 运行方式：
  ```bash
  .venv/Scripts/python -m pytest
  ```

### 9.2 定时调度

- 新增 `scripts/run_scheduler.py` 入口。
- 使用 `schedule` 库按小时周期运行全链路。
- 命令：
  - 立即执行一次：`.venv/Scripts/python scripts/run_scheduler.py --now`
  - 每 6 小时运行一次：`.venv/Scripts/python scripts/run_scheduler.py --interval 6`
- 调度器会捕获异常并继续运行，不会因为单次失败而停止。
- 建议与数据库 WAL 模式一起使用，以支撑 Web UI 与定时任务并发访问。

### 9.3 数据库并发建议

- 数据库默认已启用 `WAL` 模式与 `busy_timeout=10000`（10 秒）。
- 如果仍然遇到 `database is locked`：
  1. 确认没有其他进程持有长时间写事务。
  2. 检查是否通过 `init_db()` 重新初始化过。
  3. 考虑将高频写入模块改为批量提交。

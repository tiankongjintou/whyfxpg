# 产品风险评估系统开发报告

> 本报告阐述系统的设计目标、核心架构、开发思路与运行机制，不涉及具体技术实现细节。

---

## 一、项目背景与目标

进口机电产品的安全风险评估是海关监管的重要环节，涉及大量多源异构数据的采集、结构化处理与综合研判。传统依靠人工查阅各国监管机构公报、召回通知的方式效率低、覆盖窄、响应慢，难以适应日益复杂的国际贸易安全形势。

本系统定位为**面向进口机电产品领域的专业风险评估工具**，目标实现：

1. **多源信息自动采集** — 从多个权威国际数据源持续获取产品安全事件、召回通报、监管警示数据；
2. **标准化风险建模** — 将原始事件转化为结构化风险记录，按国别、产品类别、制造商、危害类型等多维要素进行综合评分；
3. **智能预警与闭环反馈** — 基于规则引擎自动触发预警，经人工复核后将修正信号反馈给模型，实现评估能力的持续优化；
4. **可视化研判平台** — 提供面向不同角色的操作界面，从概览仪表盘到大屏态势展示，从风险事件溯源到报告导出，满足实际业务全流程需要。

## 二、系统设计思路

### 2.1 领域驱动分层

系统的核心逻辑按照**领域模型 → 应用服务 → 端口/适配器**三层架构组织：

- **领域模型层**（`core/`）包含风险评估、预警引擎、因果推理、反馈学习等核心业务概念与规则，完全不依赖数据库、Web 框架或外部服务，独立可测；
- **应用服务层**（`services/`）编排领域逻辑，提供对外的业务操作接口，如流水线编排服务、配置管理服务、报告生成服务等；
- **端口/适配器层**（`ports/`、`adapters/`）负责与具体技术组件解耦——数据库访问通过适配器注入，外部 HTTP 数据源通过端口抽象，报告导出可替换不同格式的适配器。

这种分层的核心价值在于：**修改某一层的具体实现，不影响其他层逻辑**。例如更换数据库从 SQLite 迁移到 PostgreSQL，无需触碰领域模型；又例如调整预警规则的表现形式，只需修改 UI 层而无需重写引擎。

### 2.2 多源异构数据的统一建模

来自不同国家、机构的数据源在格式、编码、语言、分类体系上存在显著差异。系统在采集层通过**配置化适配器**（每个数据源独立配置解析规则、字段映射、字符集处理方式）将各异构输入转换为统一的**风险事件结构**：

```
风险事件 = {
    来源, 时间, 国别, 制造商, 产品名称, 产品类别,
    危害类型, 严重程度, 事件类型, 原始文本描述
}
```

这种统一建模使后续的评分、预警、汇总等所有处理逻辑均无需感知数据来源的具体差异。

### 2.3 风险评分的多维加权机制

单一维度的风险判断容易失真。系统采用**多维加权评分体系**，综合考量：

- **严重度维度** — 该类危害在国际标准中的公认严重程度；
- **概率维度** — 同类事件在历史数据中的出现频率与趋势；
- **国别维度** — 来源国别的历史合规表现与监管强度；
- **产品类别维度** — 该类别产品的整体风险特征；
- **时效性维度** — 近期事件权重高于远期，体现最新风险态势；
- **因果链维度** — 通过供应商→零部件→制造缺陷→危害类型的因果图谱传导风险。

最终评分映射至四级风险等级（S/M/L/A），支持业务人员快速决策。

### 2.4 规则与模型分离

预警规则与风险评分模型是两个关注点不同的事物：

- **风险评分模型**回答"这件事有多严重"，是定量计算，由历史数据驱动；
- **预警规则**回答"在什么条件下我需要被通知"，是条件判断，由业务策略驱动。

两者分离使业务人员可以独立调整预警触发条件而不影响评分逻辑，也使评分模型的迭代升级不会意外改变预警策略。

## 三、核心模块与运行机制

### 3.1 信息采集与解析管道

系统在后台持续运行一条**五阶段流水线**，依次为：

**采集（Collection）** — 按各数据源配置周期性地抓取网页、API 或 RSS 源，将原始页面内容存入原始页归档库并存入事件库。对于各数据源的质量（连通性、响应延迟、数据完整性和更新频率）持续打分记录。

**解析（Extraction）** — 从原始 HTML/XML/JSON 中提取结构化事件字段，包括产品信息、制造商、危害描述、监管措施等，并将其归类到统一的产品分类体系。

**评估（Evaluation）** — 对每条待评分事件调用风险评分模型，计算综合风险评分与等级，更新事件记录并重建各类汇总表。对于高风险事件（S/M 级），自动触发 LLM 辅助推理，生成结构化的风险分析文本。

**预警（Alerting）** — 逐一执行所有已启用的预警规则，将满足触发条件的规则实例化为预警记录并写入预警中心。

**归档与报告（Archiving & Reporting）** — 将本次运行的关键制品归档，生成 Word/Excel 格式的周期评估报告并存入报告库。

整个流水线由**编排器**统一驱动，记录每个阶段的开始/结束状态、耗时、错误信息，并支持失败重试。任意阶段失败不会导致整条管道中断，编排器会继续执行后续阶段并在最终报告中标注部分失败状态。

### 3.2 因果知识图谱

除了统计相关性，系统还维护了一张**因果知识图谱**，将风险事件的因果链条显式建模：

```
供应商 → 零部件类型 → 制造缺陷类别 → 危害类型 → 事故严重度
```

图谱中每个节点携带风险评分与因果权重。当某制造商被持续在复核中降级，系统会自动识别这一反馈信号并更新该制造商节点的因果评分，实现**从反馈到知识的自动积累**。

因果推理引擎支持两类操作：**正向风险传导**（给定一个风险事件，追溯其因果上游并量化各环节的风险放大系数）和**反事实推理**（模拟干预某个上游节点后重新计算最终风险，用于评估改进措施的效果）。

### 3.3 人工复核与闭环反馈

系统设有**人工复核界面**，面向专业分析师开放。复核过程记录原始评分、调整后评分、调整原因和复核人信息。这些记录进入反馈学习引擎：

- 当某国别在连续多条复核中被系统性地降级，说明模型对该国别存在系统性高估，学习引擎会分析修正一致性并给出调整建议；
- 同理适用于产品类别维度和特定制造商；
- 调整结果可选择自动应用或经人工确认后应用，形成**Bot 评分 → 人工修正 → 模型学习 → 更准的 Bot 评分**的完整飞轮。

### 3.4 配置管理与版本化

系统的各类核心参数（数据源配置、预警规则、风险模型结构、维度权重）均通过配置管理服务集中管理，支持：

- **浏览与编辑** — 所有配置对象以结构化表单而非原始 JSON 呈现，便于非技术人员理解和修改；
- **版本化发布** — 每次修改生成新版本，支持查看历史版本并一键回滚；
- **草稿机制** — 编辑内容先存为草稿，确认无误后再发布，避免误操作影响线上运行。

## 五、界面体系

系统提供两类面向不同场景的操作界面：

**监控态界面**（面向日常业务人员）包含六个主要页面：

| 页面 | 核心功能 |
|------|----------|
| 风险总览仪表盘 | 全系统风险事件分布与整体健康状态，按领域切换 |
| 风险态势大屏 | 实时核心指标与趋势，支持下钻筛选与 Excel 导出 |
| 风险事件列表 | 多维筛选查看所有事件详情 |
| 人工复核界面 | 对模型评分进行人工审核与修正 |
| 预警中心 | 集中处理预警事件 |
| 通知中心 | 流水线异常与系统事件通知 |

**管理态界面**（面向系统管理员）包含五个配置管理页面：

| 页面 | 核心功能 |
|------|----------|
| 数据源管理 | 配置外部数据源的采集规则、URL、认证方式 |
| 预警规则管理 | 配置预警触发条件与动作 |
| 风险模型管理 | 配置评分模型参数、严重度量表、风险矩阵 |
| 风险维度管理 | 配置评估维度及其权重 |
| 产品分类法管理 | 维护产品分类体系与关键词匹配规则 |

所有页面均配有**可折叠的操作指引区**，默认折叠避免干扰专业用户，需要时展开可见本页用途说明与具体操作步骤。

## 六、安全与可观测性

**操作审计** — 每次配置变更、版本发布、流水线运行均记录操作人与时间戳，支持事后追溯。

**健康监控** — 流水线各阶段、数据源连接状态、采集延迟等关键指标持续写入健康记录，可随时在数据源监控页面查看趋势。

**通知驱动** — 流水线失败、数据源长时间异常等情形自动写入通知中心，操作员登录即可见，无需主动巡检。

---

## 七、总结

本系统的核心设计哲学可以概括为三句话：

**第一，专业的事交给专业的模块。** 评分归评分，预警归预警，采集归采集，每个模块边界清晰，只做一件事。

**第二，所有核心逻辑均可替换而不影响系统其余部分。** 适配器模式贯穿全局——换数据库、换 LLM 提供商、换报告格式，均无需触碰业务逻辑。

**第三，人工经验是系统持续进化的驱动力。** 反馈学习机制确保模型不是一成不变的规则堆砌，而是随着真实复核数据的积累不断校准，真正实现人机协同的智能评估闭环。

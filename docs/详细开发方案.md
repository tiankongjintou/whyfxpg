# 进口机电产品风险评价闭环系统详细开发方案

## 1. 项目背景与定位

### 1.1 背景
本项目面向海关检验监管场景，为海关同事提供一套进口机电产品风险评价工具。系统基于半定量风险矩阵方法，结合外部公开数据源，实现信息采集、风险分析、预警、报告生成和闭环反馈。

### 1.2 定位
- 用户：海关一线检验监管人员及技术中心的业务专家
- 部署：本机原型（Windows），后期迁移至类似配置的服务器
- 数据范围：仅使用外部公开数据源，不接入海关内部涉密系统
- 数据库：SQLite（单机够用，迁移成本低）
- 开发语言：Python 3.11
- 报告形式：Word 为主，辅以数字化看板

### 1.3 关键约束
- 不接入海关内部数据，仅采集外部公开信息。
- 需要可维护：信息源、关键词、抽取规则、模型参数、预警规则全部配置化。
- 需要可审计：所有评分、预警、报告均关联配置版本和数据来源。
- 需要可解释：风险分必须能追溯到具体数据依据和规则。

### 2.2 数据充分性策略

由于无法直接获取海关进口数据，本项目采用以下策略间接获取风险信号：

1. **国际召回反推法**：CPSC、RAPEX、OPSS等召回通报中，原产国为中国以外的产品，若其出口到欧美，则进口到中国时存在类似风险。
2. **同类事故映射法**：国际通报中的产品型号、品牌、危害类型，可映射到同一制造商或同类进口产品。
3. **标准差异分析法**：通过国别标准体系与我国GB标准的差异，评估系统性风险。
4. **舆情补充法**：通过关键词监控新闻和社交媒体，发现早期风险信号。

### 2.3 数据获取技术

- **静态网页**：requests + BeautifulSoup + CSS选择器
- **动态网页**：Playwright（用于DPAC、Safety Gate等需要JS渲染的页面）
- **RSS订阅**：feedparser
- **开放数据/JSON**：直接调用API
- **变更检测**：内容哈希 + ETag，避免重复抓取
- **反爬策略**：限速、User-Agent轮换、代理池（必要时）

## 4. 可维护性设计（配置化与版本化）

### 4.1 配置化原则

所有可能变化的内容均放入YAML配置文件，代码只负责加载、解析和执行。配置文件包括：

| 配置文件 | 管理内容 |
|---|---|
| sources.yaml | 信息源URL、类型、频率、解析器、关键词引用 |
| keywords.yaml | 产品、国别、危害、标准关键词集合 |
| extract_rules.yaml | 字段抽取规则、正则、选择器、关键词映射 |
| risk_model.yaml | 严重度/概率等级、风险矩阵、修正系数、公式 |
| alert_rules.yaml | 预警条件、触发阈值、动作、优先级 |
| version_history.yaml | 配置版本与变更记录 |

### 4.2 版本化管理

每次配置变更自动记录版本，所有评估结果关联配置版本号。

**版本管理流程：**
1. 系统启动时计算各配置文件的哈希值。
2. 与上次运行保存的哈希值对比。
3. 若发生变化，自动生成新版本，并记录到 `version_history.yaml`。
4. 评估结果写入数据库时记录 `config_version`。
5. 支持按版本号回溯评估结果和参数。

### 4.3 配置加载与校验

- 使用 `pydantic` 定义配置数据模型，加载时自动校验。
- 校验失败时抛出明确错误，避免运行中使用错误配置。
- 配置变更支持热加载（无需重启程序）。

### 4.4 审计与留痕

- 所有评分记录评分依据、来源链接、模型版本、配置版本。
- 人工复核评分时，记录调整原因和调整人。
- 预警触发记录触发规则、条件命中值、处理状态。

## 5. 风险评估模型详细设计

### 5.1 模型公式

```
最终风险分 = 基础风险分 × 国别修正 × 产品修正 × 历史修正 × 证据修正

基础风险分 = SS_score × PS_score

RS_level = map_to_level(最终风险分)
```

### 5.2 严重度评分（SS）

| 等级 | 分数 | 特征描述 |
|---|---|---|
| 灾难性 | 100 | 死亡、永久残疾、重大火灾/爆炸、停工停产、重大环境污染 |
| 严重 | 90-99 | 需住院治疗、肢体截肢或严重骨折、严重经济损失 |
| 中等 | 30-89 | 门诊可治疗、人体可复原、较低经济损失 |
| 轻微 | 0-29 | 轻伤或无需治疗、经济损失可忽略 |

自动判定规则：
- 文本中出现“死亡、致死、永久残疾、重大火灾、爆炸” → 灾难性
- 出现“住院、截肢、骨折、严重伤害” → 严重
- 出现“轻伤、擦伤、门诊” → 中等
- 无明显伤害描述 → 轻微或需人工确认

### 5.3 概率评分（PS）

| 等级 | 分数 | 特征描述 |
|---|---|---|
| 非常可能 | 100 | 3年内频繁出现同类事件；未经培训人员误操作 |
| 可能 | 90-99 | 3-10年内有事件；经培训人员误操作 |
| 不太可能 | 30-89 | 10-30年内偶尔出现；采用成熟技术 |
| 几乎不可能 | 0-29 | 30年以上几乎未出现；技术可靠 |

自动判定规则：
- 基于历史事件数据库中同类产品/国别/企业的近期事件数。
- 无历史数据时，结合产品成熟度和国别标准差异推断。

### 5.4 国别修正系数（Country Factor）

| 类别 | 标准体系 | 认证监管水平 | 修正系数 |
|---|---|---|---|
| 一类（低风险） | IEC/EN/JIS/AS，与我国基本一致 | 高（CE、PSE、RCM等） | 0.9 |
| 二类（中风险） | GSO/GOST/TIS，大多采用IEC | 中 | 1.0 |
| 三类（较高风险） | UL/CSA，与IEC差异较大 | 高 | 1.1 |
| 四类（高风险） | 标准体系不完善、认证薄弱 | 低 | 1.2-1.3 |
| 未知 | 无信息 | 未知 | 1.0 |

### 5.5 产品修正系数（Product Factor）

| 产品类别 | 暴露人群 | 使用场景 | 修正系数 |
|---|---|---|---|
| 儿童相关产品 | 儿童 | 日常使用 | 1.3 |
| 家用厨房电器 | 普通消费者 | 高频密切接触 | 1.2 |
| 个人护理电器 | 普通消费者 | 与人体接触 | 1.15 |
| 照明设备 | 公共场所/家庭 | 长时间运行 | 1.05 |
| 信息技术设备 | 办公/家庭 | 长时间使用 | 1.0 |
| 普通机电 | 一般人员 | 普通场景 | 1.0 |
| 工业机床、电动工具 | 专业人员 | 有防护培训 | 0.85 |

### 5.6 历史修正系数（History Factor）

```
history_factor = 1 + 0.1 × min(recent_event_count_12m, 5)
```

- 近12个月同类产品/国别/企业事件数越多，风险越高。
- 上限1.5，避免极端放大。

### 5.7 证据修正系数（Evidence Factor）

| 数据来源 | 权威性 | 修正系数 |
|---|---|---|
| 官方召回通报（CPSC/RAPEX/DPAC/OPSS） | 高 | 1.0 |
| 海关官方公告 | 高 | 0.95 |
| 权威媒体报道 | 中 | 0.9 |
| 一般新闻/社交媒体 | 低 | 0.75 |

### 5.8 风险等级映射

| 最终风险分 | 风险等级 | 含义 |
|---|---|---|
| ≥ 8000 | S | 高风险，需重点监管 |
| 3000-7999 | M | 中等风险，加强抽查 |
| 1000-2999 | L | 低风险，常规监管 |
| < 1000 | A | 可容许风险，低优先级 |

阈值可在 `risk_model.yaml` 中配置。

### 5.9 多危害综合

若产品存在多种危害，取各危害中最高风险等级作为该产品风险等级，并在报告中列出所有危害明细。

## 6. 预警模型设计

### 6.1 预警规则类型

| 规则ID | 名称 | 条件 | 优先级 |
|---|---|---|---|
| risk_level_upgrade | 风险等级上升 | 产品风险等级从A/L上升为M/S | 高 |
| country_burst | 国别事件聚集 | 某国别30天内事件数≥3 | 中 |
| enterprise_repeat | 企业重复不合格 | 某企业365天内事件数≥2 | 高 |
| new_hazard_type | 新危害类型出现 | 某产品类别首次出现某危害类型 | 低 |
| standard_change | 标准更新 | 相关产品涉及标准发生重大更新 | 中 |
| product_category_surge | 产品类别激增 | 某产品类别事件数环比翻倍 | 中 |

### 6.2 预警动作

- 数字化看板高亮显示
- 生成预警清单Excel
- 在Word报告中单独成章
- 可选：邮件/企业微信通知（后续扩展）

### 6.3 预警状态管理

预警记录字段：
- alert_id, rule_id, triggered_at, object_type, object_value, severity, status, handled_by, handled_at, notes

状态流转：触发 → 待确认 → 已确认 → 已处理/已忽略

## 9. 在线LLM使用策略

### 9.1 可用模型供应商

- **Kimi（Anthropic兼容）**：`kimi-for-coding`，适合代码和结构化抽取。
- **MiniMax**：`MiniMax-M2.7-highspeed`，适合快速文本处理。
- **火山方舟/豆包**：`DeepSeek-V3.2`，适合推理和分类。

### 9.2 LLM使用场景

1. **信息抽取**：从召回通报文本中抽取产品、国别、企业、危害类型等字段。
2. **事件分类**：判断危害类型和严重度等级。
3. **摘要生成**：为报告生成事件摘要和趋势描述。
4. **辅助判级**：在历史数据不足时，辅助推断概率等级。

### 9.3 成本控制与可审计

- 优先使用规则抽取，LLM作为补充。
- 对LLM抽取结果保留原始提示、返回结果和置信度。
- 批量处理，减少API调用次数。
- 设置每日/每月调用限额，防止超支。

## 12. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 数据源关闭或反爬 | 采集失败 | 多源互补、缓存、代理、人工导入兜底 |
| 国际数据不适用中国 | 评估偏差 | 结合国别/标准差异修正，人工校验 |
| LLM抽取不稳定 | 字段缺失或错误 | 规则优先，LLM补充，保留置信度 |
| 模型主观性强 | 结果争议 | 透明化参数、可审计、人工复核 |
| 系统迁移复杂 | 部署困难 | 使用SQLite、Python、轻量依赖，容器化可选 |
| 维护成本高 | 项目难以持续 | 配置化设计，降低代码修改频率 |

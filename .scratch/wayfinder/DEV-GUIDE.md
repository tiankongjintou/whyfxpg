# WHYFXPG 开发指南

> 所有 Phase 1 / Phase 2 的开发任务均须遵守本指南。

---

## 一、Ticket 领取规则

1. **从 frontier 开始**：只有当一个 ticket 的所有 `Blocked by` 都已完成（或无阻塞），才能领取。
2. **独占性**：一个 ticket 同一时间只由一个 agent 领取，避免冲突。
3. **必须升级的情况**：
   - 工作量超过 2 人天
   - 发现 ticket 描述与实际代码/需求不一致
   - 需要修改其他 ticket 的范围
   - 技术选型与 `docs/技术改造路线图.md` 不符

---

## 二、开发前检查（在开始编码前必填）

- [ ] **理解 What to build**：用自己的话复述这个 ticket 要交付什么，确认与 ticket 描述一致
- [ ] **确认 scope**：我计划做的所有变更，是否都在 ticket acceptance criteria 范围内？
- [ ] **检查 blocking edges**：所有依赖的 ticket 是否已完成？如有未完成的，**不能开始**
- [ ] **对照路线图**：变更是否在 `docs/技术改造路线图.md` 该 Phase 的范围内？超范围 → **停下来询问用户**
- [ ] **探索代码库**：如未探索，先阅读相关源文件，理解现有实现后再动手
- [ ] **预重构优先**："Make the change easy, then make the easy change" — 如果现有代码阻碍实现，先做必要的预重构（作为该 ticket 的一部分）

---

## 三、开发后检查（commit 前必填）

### 3.1 功能验证
- [ ] 所有 acceptance criteria 是否满足？（每条都检查）
- [ ] 手动验证：运行相关代码路径，输出是否符合预期？

### 3.2 质量门禁
- [ ] `pytest tests/ -v` — 全部测试通过
- [ ] `ruff check whyfxpg/` — 无 ERROR
- [ ] `mypy whyfxpg/` — 无 ERROR
- [ ] 如果修改了 schema（数据库），`docs/03-数据库设计说明书.md` 已同步更新
- [ ] 如果修改了 API，`docs/04-API接口说明书.md` 已同步更新

### 3.3 Git 规范
- [ ] Commit message 格式：`[P0-N] 任务名称` 或 `[TD-N] 技术债务名称`
- [ ] Commit 前确认无调试代码、无临时注释、无 `print()` 残留

---

## 四、防止目的漂移的核心问题

开发过程中如感到迷茫，随时用这些问题自检：

| 问题 | 如果答案是"否"，说明可能已漂移 |
|------|------|
| 我现在写的代码，是否在直接服务于某个 acceptance criterion？ | → 停下来，重新对照 ticket |
| 这个改动，是否改变了系统与外部的接口（API/CLI/文件格式）？ | → 检查是否需要同步更新文档 |
| 这个改动，是否会影响其他 ticket 的依赖关系？ | → 评估影响，必要时升级 |
| 我的改动是否在 `docs/技术改造路线图.md` 规划的 Phase 范围内？ | → 超范围则停，询问用户 |

---

## 五、文档同步规则（强制）

改了代码 → **必须**同步更新对应文档：

| 变更类型 | 必须更新的文档 |
|---------|--------------|
| 数据库 schema 变更 | `docs/03-数据库设计说明书.md` |
| API 端点变更 | `docs/04-API接口说明书.md` |
| 核心算法变更 | `docs/05-核心算法说明书.md` |
| 新增数据源适配器 | `docs/全球数据源调研矩阵.md` |
| 任何影响"复现与优化"的变更 | `docs/07-复现与优化指南.md` |

---

## 六、遇到阻塞怎么办

1. 将 ticket 状态改为 `blocked`，记录阻塞原因到 ticket 文件注释中
2. 记录具体阻塞点：缺少什么信息？需要谁做决定？
3. 发飞书消息给用户，说明：
   - 哪个 ticket（P0x / TDx）
   - 阻塞原因
   - 需要用户决策的选项
4. **不要搁置**：阻塞期间可以领取其他无阻塞的 ticket 继续工作

---

## 七、紧急联系人

遇到严重问题（数据库崩溃、P0 安全漏洞、方向性问题），发飞书消息给用户。
